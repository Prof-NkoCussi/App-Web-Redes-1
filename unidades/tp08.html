24. Cliente-servidor y API REST

Recursos, endpoints y las partes de una URL

Una API (interfaz de programación de aplicaciones) es la forma en que un programa le pide datos a otro: dice qué se puede pedir y cómo. Una API REST funciona sobre HTTP, como la web (TP7, lámina 22): el cliente, nuestra página en el navegador, envía una solicitud a una URL, y el servidor de la API devuelve una respuesta con un código y los datos.

Recurso y endpoint

  • Recurso: cada cosa que ofrece la API: el dólar oficial, el clima de una ciudad, un libro de la biblioteca.
  • Endpoint: la URL donde se pide un recurso, sin los parámetros. Cada recurso tiene la suya: el del dólar oficial es https://dolarapi.com/v1/dolares/oficial
  • Consumir una API: usarla desde un programa: pedirle un recurso y usar los datos que llegan.

Las partes de una URL

Ejemplo: el clima de
Ushuaia, con Open-Meteo

https://api.open-meteo.com/v1/forecast?latitude=-54.8&longitude=-68.3&current=temperature_2m

  1. https://

    Protocolo

    HTTPS: viaja cifrado (TP7).

  2. api.open-meteo.com

    Dominio

    El servidor de la API. DNS lo traduce en una IP (TP7).

  3. /v1/forecast

    Ruta del recurso

    Qué pedimos: el pronóstico (forecast), en la versión 1 (v1) de la API.

  4. ?latitude=-54.8&longitude=-68.3&current=temperature_2m

    Parámetros

    Datos extra, después del ?: cada uno es clave=valor, y se separan con &. Acá: dónde queda Ushuaia y que mande la temperatura actual.

El endpoint es la URL sin los parámetros: https://api.open-meteo.com/v1/forecast. Con otros parámetros, da el clima de otra ciudad.

Idea clave: una API REST ofrece recursos. Cada recurso se pide en su endpoint, con una URL: protocolo, dominio, ruta y, si hacen falta, parámetros.

25. Verbos HTTP y códigos

Qué hacer con el recurso y cómo salió

En el TP7 (lámina 22) vimos que cada solicitud HTTP lleva un método, como GET. En una API REST, el método, también llamado verbo, dice qué hacer con el recurso; la URL dice cuál.

Los cuatro verbos

Ejemplo: la API de la biblioteca
de la escuela (inventada)

Las API públicas, como DolarAPI, solo dejan leer (GET): nadie de afuera puede crear, cambiar ni borrar sus datos. Para ver los cuatro verbos usamos una API inventada, la de la biblioteca de la escuela, en https://api.redesdelaula.com.

Los cuatro verbos HTTP, su acción, un ejemplo con la API de la biblioteca y el código si sale bien
VerboAcciónEn la API de la bibliotecaSi sale bien
GETLeerGET /libros/12 trae el libro 12200
POSTCrearPOST /libros crea un libro con los datos enviados201
PUTModificarPUT /libros/12 cambia el libro 12 por los datos enviados200

En JavaScript, fetch (lámina 26) envía un GET si no se le indica otro verbo.

Un POST, por dentro · crear un libro

HTTP · la solicitud
POST /libros HTTP/1.1
Host: api.redesdelaula.com
Content-Type: application/json

{"titulo": "Internet"}
HTTP · la respuesta
HTTP/1.1 201 Created
Content-Type: application/json

{"id": 13, "titulo": "Internet"}

Los datos van en el cuerpo, en JSON (lámina 26). Respuesta: 201, creado con el número 13.

Códigos de respuesta

Del TP7 retomamos 200, 404 y 500, y sumamos 201 y 400. El primer número dice cómo salió: 2, bien; 4, error en el pedido (del cliente); 5, error del servidor.

  • 200OKSalió bien.
  • 201CreatedSe creó el recurso nuevo (POST).
  • 400Bad RequestPedido mal armado: un POST sin título.
  • 404Not FoundNo existe ese recurso: /libros/999.
  • 500Internal Server ErrorFalló el servidor.

Idea clave: la URL dice qué recurso; el verbo, qué hacer: GET lee, POST crea, PUT modifica y DELETE borra. El código de respuesta dice cómo salió.

26. JSON y fetch

Pedir los datos, convertirlos y mostrarlos

Leer un JSON, el formato de las API

JSON · GET /libros/12
{
  "id": 12,
  "titulo": "Manual de redes",
  "paginas": 120,
  "prestado": true,
  "temas": ["cables", "wifi"]
}

Un objeto va entre llaves { }, con pares clave: valor separados por comas; la clave es el nombre del dato. Se lee así:

  • datos.titulo→: Manual de redestexto, entre comillas
  • datos.paginas→: 120número, sin comillas
  • datos.prestado→: truetrue o false, sin comillas
  • datos.temas[0]→: cableslista, entre [ ]; se cuenta desde 0

app.js
// Busca en la página el botón y el párrafo, por su id
const boton = document.getElementById("boton");
const resultado = document.getElementById("resultado");

// Función que pide los datos a la API y los muestra
async function consultarDolar() {
  // Le pide los datos a la API y espera la respuesta
  const respuesta = await fetch("https://dolarapi.com/v1/dolares/oficial");
  // Convierte la respuesta (JSON) en datos que JavaScript entiende
  const datos = await respuesta.json();
  // Escribe en el párrafo la compra y la venta del dólar
  resultado.textContent = "Compra: $" + datos.compra + " · Venta: $" + datos.venta;
}

// Cuando se hace clic en el botón, se ejecuta la función
boton.addEventListener("click", consultarDolar);

Idea clave: para usar otra API, cambiamos la URL y los campos del modelo.

27. MQTT

Publicar y suscribirse: mensajes entre dispositivos

MQTT es un protocolo para enviar mensajes cortos entre dispositivos: sensores, placas como el ESP32 (una placa chica con Wi-Fi que se programa) y servidores. Gasta poca memoria, poca batería y poca red; por eso se usa mucho en el Internet de las cosas (IoT).

Las partes

Puerto1883TCP

  • Broker: el servidor del medio. Recibe cada mensaje y lo entrega a los suscriptos a su tópico. En el proyecto usamos Mosquitto.
  • Publisher (publicador): publica un mensaje en un tópico.
  • Subscriber (suscriptor): se suscribe a un tópico y recibe sus mensajes.
  • Tópico: el tema del mensaje, con niveles separados por /.

Publisher y subscriber no se hablan entre sí: cada uno se conecta solo al broker.

Comparación entre HTTP y MQTT
AspectoHTTP (API REST)MQTT
Cómo se comunicanPedir y responder: el cliente pide y el servidor responde.Publicar y suscribirse: el broker reparte los mensajes.
La conexiónSe abre para cada pedido y se cierra.Queda abierta: el mensaje llega al instante.
El mensajePesado: lleva muchos headers.Liviano: el encabezado ocupa desde 2 bytes.
Cuándo convieneUna página o una app que pide datos cuando los necesita: el dólar, el clima.Dispositivos que mandan o reciben datos todo el tiempo o al instante: sensores, el ESP32.

Se usan juntos: la página le pide al servidor con HTTP, y el servidor publica en MQTT para el ESP32, que está suscripto. Así funciona el proyecto del TP10.

Idea clave: en HTTP, el cliente pide y el servidor responde. En MQTT se publica y se suscribe a tópicos: el broker reparte los mensajes por una conexión abierta.

+ Para profundizar

Las API desde el navegador, y más de JSON y MQTT

Lámina 24

Por qué algunas API no responden desde el navegador

Cuando una página le pide datos con fetch a otro dominio, el navegador revisa la respuesta antes de dársela a JavaScript. Si el servidor no la autoriza con el header Access-Control-Allow-Origin, el navegador la bloquea y fetch da error, aunque la misma URL se vea bien en la barra de direcciones.

Esta regla se llama CORS (en inglés, Cross-Origin Resource Sharing: compartir recursos entre orígenes distintos).

Las API de este TP

DolarAPI y PokéAPI responden Access-Control-Allow-Origin: *: dejan leer sus datos desde cualquier página. Si una API no lo permite, sus datos se piden desde un servidor, no desde el navegador.

Lámina 25

Ver la petición: F12 › Red

Las herramientas para desarrolladores del navegador (Chrome o Edge) muestran cada petición. Con la página abierta: F12, la pestaña Red (Network) y, después, tocar el botón o recargar la página.

Cada fila es una petición: el nombre del recurso, el Estado (el código de respuesta) y el Tipo (fetch, si la hizo JavaScript).

Una petición, por dentro

Con un clic en la fila, Encabezados muestra la URL, el método y el código; Respuesta, el JSON tal como llegó. Si algo falla, el error aparece en rojo en la pestaña Consola.

Lámina 26

Por qué JSON reemplazó a XML

Antes, muchas API respondían en XML, un formato con etiquetas, parecido al HTML. El mismo dato, en los dos formatos:

  • XML: <venta>1535</venta>
  • JSON: "venta": 1535

JSON usa menos texto, es más fácil de leer y JavaScript lo convierte directo en un objeto, con respuesta.json(). Por eso hoy casi todas las API REST responden en JSON.

Otra forma de escribir fetch

En ejemplos de Internet vas a encontrar fetch con .then() en lugar de await. Hace lo mismo; en este cuadernillo usamos siempre async y await.

Lámina 27

Tópicos con comodines

Al suscribirse se pueden usar comodines. El + reemplaza un nivel: escuela/+/temperatura recibe la temperatura de todas las aulas. El # reemplaza todos los niveles que siguen: escuela/# recibe todo lo de la escuela.

Al publicar no se usan: cada mensaje va a un tópico exacto.

MQTT cifrado

El puerto 1883 no cifra: lo que viaja se puede leer. Como HTTPS con HTTP, MQTT cifrado usa otro puerto: el 8883.

Para la práctica: dónde conseguir una API

Láminas 24 y 26

¿Dónde consigo una API?

La lista public-apis, en GitHub (github.com/public-apis/public-apis), junta cientos de API públicas, ordenadas por tema. Para usar una desde una página, como el modelo de la lámina 26, conviene que en sus columnas diga:

  • Auth: No. No pide clave ni registro.
  • HTTPS: Yes. Viaja cifrada (TP7).
  • CORS: Yes. Responde a páginas de otro dominio (Para profundizar de la lámina 24). Si dice Unknown, no se sabe: hay que probarla. PokéAPI figura así, y funciona.

Datos de Argentina

datos.gob.ar es el portal de datos abiertos del Estado argentino. Algunos datos tienen API, como Georef (apis.datos.gob.ar/georef), con provincias, municipios y calles.

Nunca subas una clave a un repositorio público

Muchas API piden una clave (API key) para saber quién las usa. Si queda en un repositorio público, como uno de GitHub, cualquiera puede verla y usarla a tu nombre.
