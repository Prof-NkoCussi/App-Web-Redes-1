31. Mapa del proyecto

Qué viaja, por dónde y con qué protocolo

YoLo v1 es un robot con cámara que se maneja desde una página web. Tiene una placa ESP32-CAM (un ESP32 con cámara, TP8), motores y un sensor de obstáculos. Este mapa muestra cómo se comunican las partes del proyecto.

Los cinco comandos

Todos van a POST /api/comando; cambia solo el comando del JSON. Se escriben tal cual: en minúscula y sin tilde.

Los cinco comandos y qué hace el robot con cada uno
ComandoEl robot…
adelanteavanza
atrasva hacia atrás
izquierdagira a la izquierda
derechagira a la derecha
stopse detiene

El sensor de obstáculos

Si hay un obstáculo a menos de 15 cm, el robot no avanza: puede ir hacia atrás o girar para salir.

El recorrido de un comando

Cuando apretás un botón, el comando hace este recorrido:

  1. 1App → servidor (HTTP). El botón hace un fetch al endpoint POST /api/comando con un JSON, por ejemplo {"accion":"adelante"}.
  2. 2Servidor → broker (MQTT). El servidor publica el comando en el tópico del robot.
  3. 3Broker → robot (MQTT). El robot está suscripto a ese tópico, recibe el comando y mueve los motores.

En el paso 1, el servidor le contesta a la app con un código de respuesta (TP8, lámina 25).

El video hace otro camino: sale de la cámara del robot y llega directo al navegador por HTTP, sin pasar por el servidor.

Idea clave: el comando va de la app al servidor por HTTP (puerto 3000) y del servidor al robot por MQTT, a través del broker (puerto 1883). El video va directo del robot a la app, por HTTP.

Lámina 31 · Etapa 4

El fetch, el JSON y el código: F12 › Red

Como en el TP8 (Para profundizar de la lámina 25): con la app abierta en Chrome o Edge, F12, la pestaña Red (Network) y tocar un botón. Cada fetch es una fila: el Nombre es el final de la URL, el Estado es el código de respuesta y el Tipo, fetch. El filtro Fetch y XHR deja solo los pedidos de JavaScript.

Con un clic en la fila:

  • Encabezados: la URL de solicitud, el método (POST) y el código de estado.
  • Carga útil (Payload): el JSON que mandó el botón.
  • Respuesta: lo que contestó el servidor.

Cómo leer el Estado

  • 2…: salió bien; por ejemplo, 200 OK (TP8, lámina 25).
  • 4…: error en el pedido: 400, mal armado; 404, ese endpoint no existe.
  • 5…: falló el servidor.
  • (ha fallado), en rojo y sin código: el pedido no llegó al servidor. Revisá la IP y el puerto de la URL.

Lámina 31 · TP7 y TP8

Los puertos del servidor y del broker

  • Puerto3000TCP

    Servidor Node.js + Express: atiende HTTP.

  • Puerto1883TCP

    Broker Mosquitto: atiende MQTT.

La IP dice a qué equipo va cada mensaje, y el puerto, a qué aplicación (TP7, lámina 20). El servidor y el broker están en la misma PC: tienen la misma IP y se distinguen por el puerto.

Los dos tramos de MQTT usan el puerto del broker: el servidor y el robot se conectan los dos al broker, en el 1883 (TP8, lámina 27).

El puerto en la URL

Sin número, una URL con http:// va al puerto 80 (TP7). Como el servidor escucha en el 3000, la URL lo lleva después de dos puntos:

http://192.168.1.10:3000/api/comando

El 3000 y el 1883 son puertos registrados: del 1024 al 49151 (TP7, lámina 20).

Para la defensa: las IP y el video

Lámina 31 · TP9 · Etapa 2

Qué IP tiene cada parte y cómo se asigna

La app le manda los comandos al servidor a su IP; el robot se conecta al broker con su IP; y la app le pide el video al robot a su IP. Si alguna de esas IP cambiara, no se encontrarían: por eso la PC del servidor y el robot llevan una IP que no cambia, fija o reservada (TP9).

Las partes del proyecto, una IP de ejemplo para cada una y cómo se asigna
ParteIP de ejemploCómo se asigna
Router192.168.1.1Es la puerta de enlace de la red (TP9, lámina 29).
PC del servidor (servidor y broker)192.168.1.10Fija, puesta en Windows (TP9, lámina 28), o reservada en el router. Fuera del rango DHCP.
Robot YoLo192.168.1.20Reservada en el router, con la MAC del robot (TP9, lámina 30). El robot no se abre: su IP se asigna desde el router.
Notebook o celular con la app192.168.1.25Dinámica, por DHCP: nadie tiene que encontrarla, porque la app empieza cada pedido.

Dónde se ve cada IP

En el router, en la lista de dispositivos conectados, con su MAC (TP9, lámina 30): ahí aparecen el robot y la PC del servidor. En una PC, con ipconfig (TP9, lámina 28).

Son IP de ejemplo

Usan la red 192.168.1.0 del cuadernillo. Las de tu grupo las sacás de tu router: son las que van en el esquema de red.

Lámina 31

Por qué el video no pasa por el servidor

El video de la cámara es MJPEG (Motion JPEG): una foto JPEG detrás de otra, varias por segundo, que llegan por una misma respuesta HTTP que no termina. Para el video, el robot hace de servidor: la app se lo pide a la IP del robot.

Si pasara por el servidor, cada foto viajaría dos veces por el Wi-Fi (robot → servidor → app): el doble de tráfico, más demora y más trabajo para el servidor. Directo, llega antes.

¿Y por MQTT?

MQTT es para mensajes cortos (TP8, lámina 27): {"accion":"stop"} ocupa 17 bytes; una sola foto, miles. Por eso los comandos van por MQTT y el video, por HTTP.

Consigna: En grupo, van a hacer andar a YoLo: un robot con cámara que se maneja desde una página web, sobre una red que arman ustedes. Al final lo defienden en vivo.

¿Qué es el TP final?

El TP10 es el trabajo final de Redes I y de Software II. Es uno solo y vale para las dos materias: un mismo proyecto, una misma entrega y una misma defensa.

No hay teoría nueva. Van a usar lo que ya vieron en el año, pero todo junto y funcionando de verdad:

  • De Redes I: HTTP, puertos, API REST, JSON, MQTT y la configuración del router.
  • De Software II: el ambiente de desarrollo, HTML y CSS, Git y GitHub, el tablero de Trello y la documentación.
  • De Programación II: JavaScript, para programar los botones.
Datos del TP final
GruposDe 2 integrantes
CierreDefensa oral con el robot funcionando
FechasEn Classroom

El objetivo

Entender cómo se comunican las partes de un sistema conectado y demostrarlo haciéndolo andar. No alcanza con que el robot se mueva: tienen que poder explicar qué viaja, por dónde y con qué protocolo.

Al terminar el TP, el grupo tiene que poder:

  1. Configurar un router con una red Wi-Fi propia y direcciones IP fijas o reservadas.
  2. Comprobar que el robot y el servidor responden.
  3. Programar los botones de la app para que manden los comandos con fetch y JSON.
  4. Diseñar la app con HTML y CSS y mostrar el video del robot.
  5. Trabajar en equipo en GitHub: commits claros.
  6. Documentar el proyecto para que otra persona lo pueda instalar y usar.
  7. Explicar y defender cada decisión en forma oral.

La bitácora

Al final de cada clase, anoten en la bitácora (BITACORA.md) qué hicieron, qué problemas tuvieron y qué decidieron. Eso también se evalúa.

Cómo se evalúa

Se evalúa todo el recorrido, no solo el día de la defensa. GitHub y Trello muestran quién hizo cada commit y cada tarea, así que cada integrante tiene que aportar.

Redes I mira tres cosas:

  • Que la app funcione y se comunique con el servidor.
  • Que en la defensa los comandos lleguen al robot con una conexión estable, y que sepan explicar qué protocolo interviene en cada tramo.
  • Que la documentación tenga el esquema de red, el manual de uso y el código.

Software II reparte la nota así:

Cómo reparte la nota Software II: parte, peso y qué se mira
PartePesoQué se mira
Producto40 %La app funciona, el repositorio está ordenado y el README alcanza para instalar el proyecto
Proceso35 %Todos hacen commits; tablero y bitácora al día; cumplen el plan
Defensa25 %Cada integrante explica y responde preguntas

La defensa

Muestran el robot funcionando en vivo y explican el proyecto. Cada integrante tiene que poder responder preguntas como estas:

  • ¿Qué protocolo viaja entre la app y el servidor? ¿Y entre el servidor y el robot? Lámina 31
  • ¿En qué puerto escucha el servidor? ¿Y el broker? Lámina 31 · Para profundizar
  • ¿Qué IP tiene el robot y cómo se la asignaron? Para profundizar · TP9
  • ¿Qué hace el fetch de un botón? ¿Qué JSON manda y qué código de respuesta vuelve? Lámina 31 · Para profundizar
  • ¿Por qué el video no pasa por el servidor? Para profundizar
  • ¿Qué hiciste vos, cuál fue tu rol en el grupo? Su trabajo

Reglas y cuidados

  • El robot no se abre. No se desconectan cables ni se tocan las placas. El trabajo es de red y de software.
  • Las baterías las maneja solo el docente. Si notan que el robot se reinicia o anda lento, avisen: probablemente necesita carga.
  • Prueben el robot en el piso o con las ruedas en el aire, nunca al borde de la mesa.
  • La red del robot es solo para el proyecto. No la conecten a otras redes ni cambien la configuración de otro grupo.
  • Si se traban, pregunten. Los errores son parte del trabajo: antes de preguntar, revisen la pestaña Red del navegador y lean el código de respuesta.
